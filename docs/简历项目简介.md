# 低代码表单生成 Agent（个人项目 · 简历版）

> 一句话：用一句自然语言需求，生成强类型、可渲染、可校验、可审批的表单 Schema —— 一个把 LLM 不确定性收敛成确定性产物的最小闭环。

| 角色     | 独立开发（AI 服务 + 网关 + 前端 + 容器化部署）                                                                                                                                                   |

## 二、系统架构

```
浏览器 / 调用方
   │  /api（同源，Vite 或 Nginx 反代）
   ▼
NestJS 网关 (3000)          统一入口、class-validator 参数白名单、上游错误包装
   │  HTTP
   ▼
FastAPI Agent (8000)         LangGraph 状态机编排
   │
   ├─ retrieve    LangChain RAG：规范文档召回（向量索引 + 关键词兜底）
   ├─ generate    PydanticAI：输出强类型 FormSchema（Pydantic v2 校验）
   ├─ check       规则校验：标题/字段非空、字段名唯一、语义一致性
   ├─ approval    合格 → 待人工审批 / 自动通过；不合格且未超上限 → 回到 generate
   └─ steps       非节点：各节点写入的执行轨迹，接口原样返回 → 前端时间线
```

LangGraph 条件边承担「失败重生成」循环（`MAX_RETRY=2`，即最多 2 轮生成），一次生成被建模成带 `run_id` 的运行实例，对外暴露 5 种状态：`pending / pending_approval / auto_passed / approved / rejected`。节点之间通过带累加 reducer 的 `steps` 传递执行轨迹，循环是否真的发生过，在页面上能直接看出来。

## 三、核心工作（详细版，可直接改写为简历 bullet）

1. **设计四节点 LangGraph 状态机，并让它可观测**：把「检索 → 生成 → 校验 → 审批」拆成独立节点，用条件边实现校验失败回到生成节点重生成（`MAX_RETRY` 是生成轮次上限），并用 `run_id` 管理运行态生命周期。每个节点向带累加 reducer 的 `steps` 写入一条轨迹——检索模式与命中片段、第几轮生成及走 LLM 还是规则兜底、校验结论、审批动作——接口原样返回、前端渲染成时间线；对外只留一个语义含糊的 `retries` 时，既看不出循环有没有触发，也无法自证。
2. **以强类型约束 LLM 输出，并分清两层重试**：用 PydanticAI 将生成结果约束为 `FormSchema`（Pydantic v2 模型），字段类型收敛为 15 种契约（text/tel/email/password/textarea/select/radio/checkbox/switch/number/date/time/datetime/upload/url）。**结构/类型不合法由 PydanticAI 在生成节点内修复（`Agent(retries=3)`），耗尽后本次降级规则生成；图层面的循环只管 4 条业务规则校验**（标题/字段非空、字段名唯一、需求含"手机/电话/联系方式"必须有 `phone`）。前者管"能不能解析"，后者管"符不符合需求"，避免"能渲染但字段错"的隐性故障。
3. **RAG 规范召回的工程化改造**：原实现每次查询都要对每个 chunk 重新做 embedding，改为**一次性构建索引 + 归一化矩阵 + npz 磁盘缓存**，单次查询的 embedding 调用由 N 次降为 1 次；缓存签名绑定 chunk 内容 / embedding 模型 / base_url，任一变化自动重建；embedding 服务不可用时自动降级为关键词重叠检索，保证链路不中断。
4. **设计离线可运行的规则兜底生成器**：在无 LLM 密钥、无外网的条件下，用规则引擎覆盖 15 类字段识别（含"性别→单选 / 爱好→多选 / 协议→开关 / 预约→日期时间"等语义映射），按提示词中首次出现的位置排序、按字段名去重，使整条 Agent 链路（含循环、审批）可在本机完整演示，实测平均响应 21ms。
5. **前端表单渲染与流程可视化**：React 18 + Ant Design 5 实现 15 类控件渲染（`Radio.Group` / `Checkbox.Group` / `Switch`(`checked`) / `Upload`(`fileList`) / `DatePicker showTime` / `Input.Password` / `InputNumber`），按字段类型施加必填与 email/url/tel 格式校验，提供"校验表单 / 重置"与归一化结果回显（dayjs、上传文件转可读值）；任务卡片用 `Timeline` 还原 `steps` 轨迹（绿=通过、红=失败、蓝=无判定），并把含糊的"重试次数"改成"生成 N 轮 · 重试 M 次"。响应式采用 `clamp()` 字号与间距、`flex-wrap` 操作区、480px 断点收紧卡片内边距，控件区 390px 视口实测无横向溢出（`scrollWidth=390`）。
6. **网关与错误契约**：NestJS 侧用 `ValidationPipe({ whitelist: true })` 做参数白名单校验，把上游不可达包装为 502、参数非法为 400，前端不接触裸 500；同时统一字段契约（`requirement` / `need_approval` / `form_schema` / `approved`）。
7. **容器化与部署约束推导**：三服务 Docker Compose（agent / gateway / web），Nginx 托管静态资源并把 `/api` 反代到网关，仅暴露 80；由于运行态 `_RUN_STORE` 存在进程内存，明确得出「uvicorn 单 worker、副本固定 1」的部署约束，并写入文档——扩容前必须先迁移 Redis/DB。

## 四、关键难点与解法（面试可展开）

**1. 框架版本漂移导致的"静默失效"**

`pydantic-ai` 2.x 移除了 `OpenAIModel` 与 `result_type`，而原代码用 `try/except` 包住初始化——结果是导入失败被吞掉，`_agent=None`，**即使配了 API Key 也永远走规则兜底**，表面看"能用"，实际 LLM 从未被调用。
定位方式：直接对照已安装版本的函数签名（`inspect.signature`），确认构造器与输出参数已改名；改为 `OpenAIChatModel` + `OpenAIProvider(base_url, api_key)` + `output_type=FormSchema`，并将模型调用失败改为「本次降级规则、不抛 500」。

后续把这条降级路径做成可见的：`steps` 里生成节点标出「LLM」还是「规则兜底」，静默失效在页面上一眼可辨。实际就是这样发现本机 shell 的 `no_proxy` 含 `[::1]` 会让 httpx 构造客户端失败、整条链路一直走规则兜底——表面 200，模型从未被调用。

**2. RAG 检索的性能陷阱**

原实现对每个 chunk 逐个 `embed_documents`，chunk 越多越慢，且每次请求重复计费。改造为：一次批量 embedding → L2 归一化 → 存 `npz` → 查询时只做一次 `embed_query` 和一次矩阵乘法；用签名做缓存失效，避免"改了文档还用旧索引"。

**3. 规则生成的语义冲突**

日期/时间字段原用 `if/elif`，导致需求里同时出现"参加日期 + 预约时间"时只生成一个字段（被 `datetime` 分支抢先命中）。解法：改为独立判断 + 字段名去重 + 通用类型只在无更具体字段时补充，并按提示词位置排序，字段顺序与用户描述一致。

**4. 从代码事实推导部署形态**

常驻进程 + 进程内存状态 → 云函数、纯静态托管均不可行；内存态 run store → 不能多副本。结论是「单机 + 单副本 + 反向代理」，并把这条约束写进 README/部署文档，而不是等上线后踩坑。

**5. 「重试次数」恒为 1：指标语义与实现对不上**

`retries` 记的是 generate 节点执行次数，一次通过也显示 1，既看不出循环有没有触发，也没法向面试官证明它存在。根因是校验只有 4 条硬约束，而规则兜底产物必然满足，循环在演示里几乎不会启动。

解法分三步：状态里加 `steps`（`Annotated[list, operator.add]`）由每个节点写增量；对外 `retries` 改为「重生成次数 = 轮次 - 1」，一次通过返回 0，与字段自身的描述对齐；前端用时间线还原链路。验证方式不是靠读代码，而是把 `_validate` 临时加严一条规则，页面立刻出现第 2 轮 `generate` / `check`、状态转 `rejected`。

## 六、简历精简版（3 条，空间有限时用）

- 独立开发低代码表单生成 Agent（FastAPI + LangGraph + PydanticAI + LangChain，React + NestJS 三层架构），将自然语言需求转成强类型表单 Schema，支持 15 种字段类型、校验失败自动重生成与人工审批闭环。
- 设计 `retrieve → generate → check → approval` 四节点状态机与 `run_id` 生命周期，用带累加 reducer 的 `steps` 记录每个节点的执行轨迹并在前端时间线还原，把语义含糊的「重试次数」修正为重生成次数；将 RAG 检索改为一次性建索引 + 磁盘缓存，单次查询 embedding 调用由 N 次降至 1 次；模型或 embedding 不可用时自动降级关键词检索与规则生成，保证离线可演示。
- 完成三服务容器化（Docker Compose + Nginx 同源反代），由"运行态在内存"推导出单 worker/单副本约束并写入文档；前端实现 15 类控件渲染与校验，390px 移动端实测无横向溢出。

## 七、面试追问预案

| 追问                                      | 回答要点                                                                                   |
| ----------------------------------------- | ------------------------------------------------------------------------------------------ |
| 为什么用 LangGraph 而不是直接串函数？     | 校验失败要回到生成节点形成循环，且需要显式状态与条件边；节点轨迹靠带累加 reducer 的 `steps` 传递，后续可替换 checkpointer 做断点续跑 |
| 两层重试分别是什么？                      | PydanticAI 节点内 3 次输出修复，管"结构能不能解析"；LangGraph 图层面的重生成循环，管"业务规则满不满足"，上限 `MAX_RETRY` 轮 |
| 循环上限怎么现场验证？                    | 把 `_validate` 临时加严一条规则（如字段数下限），时间线立刻出现第 2 轮 `generate` / `check`，`retries` 从 0 变 1，最终 `rejected` |
| 为什么用 PydanticAI 而不是自己解析 JSON？ | 输出受 Pydantic 模型约束，类型不合法在生成节点内立即重试修复（3 次），耗尽才降级规则生成，避免脏数据流入前端 |
| RAG 的召回质量怎么保证？                  | 目前是余弦相似度 + 关键词兜底，规范文档 9 个 chunk；规模化后应换向量库并加入 rerank        |
| 单副本的限制怎么解除？                    | 把 `_RUN_STORE` 换 Redis/DB 或 LangGraph checkpointer，之后才能水平扩容                    |
| 前端如何兼容未知字段类型？                | 渲染层按 `type` 分发，未知类型回退 `Input`，避免新增类型导致页面崩溃                       |

## 八、诚实边界（写简历时避免夸大）

- 规模是个人项目：单机、单副本、无鉴权、无持久化，未做压测与高并发验证。
- LLM 走 OpenAI 兼容接口，当前对接智谱 `glm-4-flash`（对话）+ `embedding-3`（RAG 向量化），需自备 Key 与额度；未配置 Key 或调用失败时自动降级为规则生成 + 关键词检索，保证无密钥也能离线演示（LLM 路径与降级路径均已实测）。
- 上传字段目前是前端占位（`beforeUpload` 拦截），后端无上传接口，文件不会落盘。
- `/generate` 是同步接口，跑完整条图才返回终态；前端保留的 1.5s 轮询只用于兜底刷新，异步任务化（先返回 `pending`、后台跑图、进度实时推进）还没做。
- 校验只有 4 条硬约束，语义质量靠人工审批兜底，没有自动评估——所以正常演示里循环通常不触发，要多轮就得临时加严规则。
- `steps` 与运行态同在进程内存，服务重启即丢，历史任务无法回放。
- 时间线渲染只在桌面宽度实测过，390px 窄屏未复测（此前的移动端实测只覆盖控件区）。
